# Von Next.js nach Nexy migrieren

Next.js hat dateibasierte Routing- und Serverkomponenten populär gemacht. Nexy bringt das gleiche DX zu Python.

## Konzeptzuordnung

| Next.js | Nexy |
|---------|------|
| `app/` Verzeichnis | `src/routes/` Verzeichnis |
| `page.tsx` | `.nexy` oder `.mdx` Datei |
| `layout.tsx` | `layout.nexy` |
| `loading.tsx` | `dependencies.py` |
| `route.ts` (API) | `.py`-Datei mit `get()`, `post()` usw. |
| `next.config.js` | `nexyconfig.py` |
| Serveraktionen | `"@Action` Dekorateur |
| React-Server-Komponenten | `.nexy` Komponenten (Python + Jinja2) |
| `getStaticProps` | Frontmatter-Logik in `.nexy` |

## Beispiel

```python
# Next.js: app/users/[id]/page.tsx
export default async function Page({ params }) {
    const user = await db.user.findUnique(params.id);
    return <div>{user.name}</div>;
}

# Nexy: src/routes/users/[id]/index.nexy
---
user = db.user.find_unique(id)
---
<h1>{{ user.name }}</h1>
```

## Migrationsschritte

1. **Gerüst** – `nx new my-app`
2. **Portseiten** – `page.tsx` → `.nexy` oder `.mdx` Dateien
3. **Port-Layouts** – `layout.tsx` → `layout.nexy`
4. **Port-API-Routen** – `route.ts` → `.py` Dateien mit `get()`, `post()` usw.
5. **Portserveraktionen** – Serveraktionen → `"@Action` Dekorator

## Hauptunterschiede

- **Python auf dem Server** – kein JavaScript/TypeScript erforderlich
- **Kein Build-Schritt für Seiten** – `.nexy`-Dateien werden zur Entwicklungszeit kompiliert
- **Mehrere Frontend-Frameworks** – React, Vue, Svelte, Solid, Preact
- **FastAPI unter der Haube** – asynchron, OpenAPI, typsicher
- **Zwei Routing-Strategien** – dateibasiert (wie Next.js Pages) oder modular (wie NestJS)
