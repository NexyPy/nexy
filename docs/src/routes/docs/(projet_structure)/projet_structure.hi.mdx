# परियोजना संरचना

यह पृष्ठ नेक्सी की फ़ाइल और फ़ोल्डर परंपराओं का एक सिंहावलोकन देता है, और अपने प्रोजेक्ट को कैसे व्यवस्थित करें।

```text
my-app/
├── .venv/
├── node_modules/          (optional — client framework only)
├── public/
├── src/
│   ├── components/
│   ├── routes/            (FBR) — or apps/ (Modular)
│   └── layout.nexy
├── .gitignore
├── nexyconfig.py
├── pyproject.toml
├── package.json           (optional)
├── vite.config.ts         (optional)
└── tsconfig.json          (optional)
```

---

## शीर्ष-स्तरीय निर्देशिकाएँ

### `public/`

यहां रखी गई स्थिर संपत्तियां रूट `/` URL पर परोसी जाती हैं। छवियाँ, फ़ॉन्ट, फ़ेविकॉन, robots.txt - कुछ भी जिसे आप बिना रूट के सार्वजनिक रूप से एक्सेस करना चाहते हैं।

### `src/`

आपका एप्लिकेशन स्रोत कोड यहां रहता है। नेक्सी विकास में परिवर्तनों के लिए `src/` देखता है और यहां से उत्पादन में सब कुछ संकलित करता है।

---

## अंदर `src/`

```text
src/
├── components/     — reusable Nexy components (optional)
├── routes/         — FBR: file-based routing tree
├── apps/           — Modular: controllers, modules, providers
├── layout.nexy     — root layout (optional, FBR only)
└── global.css      — global styles (optional)
```

### `src/components/`

पुन: प्रयोज्य `.nexy` घटकों के लिए वैकल्पिक निर्देशिका। नेक्सी किसी विशिष्ट घटक निर्देशिका को लागू नहीं करता है - आप किसी भी नाम या संरचना का उपयोग कर सकते हैं। घटक `from "@components/..." import ...` के साथ आयात किए जाते हैं।

### `src/routes/` (फ़ाइल-आधारित रूटिंग)

`src/routes/` के अंतर्गत प्रत्येक `.py`, `.nexy`, और `.mdx` फ़ाइल एक HTTP रूट बन जाती है, विशेष फ़ाइल नामों के अपवाद के साथ:

| फ़ाइल | व्यवहार |
|------|----------|
| `index.nexy` / `index.py` / `index.mdx` | मूल पथ पर सेवा दी गई (`/users/index.nexy` → `/users`) |
| `layout.nexy` | सहोदर और बाल मार्गों के लिए साझा लेआउट (रूटेबल नहीं) |
| `__init__.py` | पायथन पैकेज मार्कर (रूटेबल नहीं) |
| `dependencies.py` | साझा निर्भरताएँ (परिवर्तनीय नहीं) |

```text
routes/
├── index.nexy          →  /
├── about.nexy          →  /about
├── blog/
│   ├── index.nexy      →  /blog
│   ├── [slug].nexy     →  /blog/{slug}
│   └── layout.nexy     —  shared layout for /blog/*
└── api/
    └── users.py        →  /api/users (GET, POST, etc.)
```

### `src/apps/` (मॉड्यूलर रूटिंग)

मॉड्यूलर राउटर का उपयोग करते समय, आपका एप्लिकेशन कोड फीचर मॉड्यूल में व्यवस्थित होता है:

```text
apps/
├── app_module.py       →  "@Module(root module)
├── app_controller.py   →  "@Controller("/")
├── app_view.nexy       →  template
├── users/
│   ├── user_module.py
│   ├── user_controller.py
│   └── user_service.py
└── layout.nexy         →  shared layout
```

## कॉन्फ़िगरेशन फ़ाइलें

| फ़ाइल | उद्देश्य |
|------|---------|
| `nexyconfig.py` | मुख्य नेक्सी कॉन्फ़िगरेशन: राउटर, प्लगइन्स, ऐप सेटिंग्स |
| `pyproject.toml` | पायथन प्रोजेक्ट मेटाडेटा, निर्भरताएं, बिल्ड सिस्टम |
| `package.json` | जावास्क्रिप्ट निर्भरताएँ (क्लाइंट फ्रेमवर्क का उपयोग करते समय मौजूद) |
| `vite.config.ts` | क्लाइंट-साइड कोड को बंडल करने के लिए वाइट कॉन्फ़िगरेशन |
| `tsconfig.json` | टाइपस्क्रिप्ट कंपाइलर विकल्प |
| `.gitignore` | फ़ाइलों और निर्देशिकाओं को संस्करण नियंत्रण से बाहर रखा जाए |

---

## अपने प्रोजेक्ट को व्यवस्थित करना

उपरोक्त परंपराओं के अलावा, आप अपने स्रोत कोड की संरचना कैसे करते हैं, इस पर नेक्सी की कोई राय नहीं है। कुछ पैटर्न जो अच्छे से काम करते हैं:

- **फ़ीचर फ़ोल्डर**: संबंधित पृष्ठों, घटकों और उपयोगिताओं को फ़ीचर के अनुसार समूहित करें
- **साझा घटक**: वास्तव में पुन: प्रयोज्य घटकों को `src/components/` में रखें
- **रूट समूह**: आपकी यूआरएल संरचना को प्रतिबिंबित करने के लिए `src/routes/` में नेस्ट निर्देशिकाएँ
- **मोनोरेपो**: `src/apps/` मॉड्यूल को स्वतंत्र रूप से तैनात करने योग्य इकाइयों के रूप में मानें

जो बात मायने रखती है वह यह है कि `src/routes/` (FBR) के अंतर्गत या `"@Module` (मॉड्यूलर) द्वारा संदर्भित प्रत्येक फ़ाइल उपरोक्त नामकरण परंपराओं का पालन करती है।
