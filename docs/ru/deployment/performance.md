# Производительность

Что `nx start` делает по умолчанию, что включать и что измерялось.

## По умолчанию

| Проблема | По умолчанию | Измените |
|---|---|---|
| Обрабатывает | один Uvicorn рабочий процесс на каждый процессор в Linux и macOS, один в Windows | `nx start` запускает приложение через Uvicorn |
| Сжатие | отключено | `useGZip = {"minimum_size": 1000}` в [Конфигурация](../reference/config.md) или сжатие на обратном прокси-сервере |
| Статические файлы | обслуживаются с помощью `ETag` и `Last-Modified`, нет `Cache-Control` | устанавливает долговременное кэширование на обратном прокси-сервере или CDN для хешированных пакетов |
| HTML-страницы | отображаются по запросу, без кеша | [ISR](../rendering/isr.md) с `revalidate = N` |
| Документы API | на | `useDocs = False` в производстве |
| Узел во время выполнения | нет | `nx build` выполняет предварительную визуализацию клиентских компонентов |

## Измеренный

Локальный запуск, один Uvicorn рабочий процесс, Windows, Python 3.13, поддерживающие соединения от генератора нагрузки Python на той же машине. Рассматривайте цифры как основу для сравнения изменений, а не как эталон по сравнению с другими платформами.

| Маршрут | Параллелизм | Запросов в секунду | p50 | p99 |
|---|---|---|---|---|
| Пустой FastAPI Маршрут JSON | 16 | ~4500 | 3,4 мс | 5,1 мс |
| Маршрут Nexy JSON (`src/routes/api/ping.py`) | 16 | ~2900 | 5,2 мс | 9,8 мс |
| Страница Nexy SSR (16 КБ, 16 компонентов) | 1 | ~500 | 1,9 мс | 3,0 мс |
| Страница Nexy SSR (16 КБ, 16 компонентов) | 64 | ~670 | 94 мс | 126 мс |

Читаем таблицу:

- Собственные уровни Nexy (контекст пути, промежуточное программное обеспечение) стоят примерно треть пропускной способности чистого FastAPI маршрута.
- Страница, отображаемая на сервере, требует около 2 мс процессорного времени и распределяется примерно по 16 рендерингам шаблонов (по одному на каждый компонент). Страницы с меньшим количеством компонентов пропорционально дешевле.
- Пропускная способность масштабируется вместе с рабочими. В Linux `nx start` уже запускается по одному на каждый процессор.

## Практические советы

1. Поставьте Nginx, Caddy или преимущество вашей платформы: TLS, HTTP/2, Brotli и долговременное кэширование для ресурсов `/__nexy__/client/` — их сильные стороны. См. [Развертывание](README.md).
2. Используйте [ISR](../rendering/isr.md) для страниц, которые изменяются реже, чем раз в минуту.
3. Делайте гидратацию лениво с помощью [островов](../rendering/islands.md), чтобы при первой загрузке было отправлено меньше JavaScript.
4. Количество `.nexy` компонентов на странице должно быть разумным: каждый из них представляет собой отдельный рендеринг шаблона.
5. Измерьте свои собственные маршруты. Локального генератора нагрузки, поддерживающего соединения, достаточно для сравнения двух версий страницы.
