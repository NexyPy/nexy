# Как работает Некси

Ментальная модель на одной странице: что строит Nexy, что строит Vite и что происходит между файлом и страницей в вашем браузере. Прочтите это один раз; остальная документация представляет собой набор деталей.

## Архитектура Некси

Запрос пересекает пять уровней: Uvicorn принимает его, промежуточное программное обеспечение украшает его, маршрутизатор выбирает файл, средство рендеринга преобразует этот файл в HTML или JSON, а клиентский уровень берет на себя управление, если на странице есть JavaScript. Nexy владеет средней тройкой; Vite и ваш фреймворк владеет клиентом; ваше приложение владеет данными, аутентификацией и авторизацией.

Каждый уровень и то, что он отказывается делать, находятся в [Архитектура](../architecture.md). Пакеты самого Nexy см. в `ARCHITECTURE.md` в корне репозитория — они написаны для участников.

## Жизненный цикл приложения

`nx dev` перед первым запросом выполняет шесть действий:

1. проверяет `nexyconfig.py` и останавливается на неверной конфигурации;
2. обеспечивает возможность импорта пакетов проекта Python;
3. разрешает порты и удаляет устаревший маркер `__nexy__/nexy.prod`;
4. параллельно генерирует клиентские файлы и компилирует маршруты;
5. запускает Vite и ждет, пока он ответит;
6. устанавливает наблюдатель файлов, а затем позволяет uvicorn импортировать `nexy.modules.routers.app:_server`.

Этот импорт собирает приложение — промежуточное ПО, действия, маршрутизаторы, обработчики ошибок — и первый запрос обслуживается этой сборкой. При сохранении наблюдатель перезапускает uvicorn; страница, которая появилась, исчезла или переместилась, также восстанавливает список маршрутов клиента.

## Система маршрутизации

Путь под `src/routes/` становится URL-адресом по четырем правилам:

| URL-адрес файла | |
|---|---|
| `blog/index.nexy` | `/blog` |
| `blog/[slug].nexy` | `/blog/hello` |
| `blog/[...parts].nexy` | `/blog/a/b` |
| `(marketing)/about.nexy` | `/about` |

Расширение никогда не появляется; `index` — маршрут к папке; папка в скобках группирует файлы без добавления сегмента.

Когда два объекта могут ответить на один и тот же URL-адрес, **побеждает тот, кто зарегистрировался первым**, и Nexy всегда регистрируется в следующем порядке:

1. конечная точка Действия;
2. статические файлы: `/public`, `/assets`, `/favicon.ico`;
3. модульный `APIRouter` (`useRouter`);
4. файловые маршруты, сначала наиболее конкретные: статические пути, затем динамические пути с наиболее фиксированными сегментами, а затем всеобъемлющие.

Два файловых маршрута одинаковой специфичности регистрируются в алфавитном порядке, поэтому `[id].nexy` отвечает перед `[slug].nexy`. Таким образом, модульный маршрут превосходит страницу с тем же путем. Это порядок приоритета, на который можно положиться, а не правило тай-брейка: дайте одному URL-адресу один файл.

## Система просмотра

Расширение файла определяет, что это такое, а конфигурация проекта определяет, какие расширения активны.

| Расширение | Активно, когда | Составлен | Служит как |
|---|---|---|---|
| `.nexy` | режим сервера | Nexy: заголовок становится Python, разметка становится Jinja2 | страницей |
| `.md` | всегда | Nexy: с поддержкой GitHub Markdown, идентификаторы заголовков, оглавление | страница, внутри ближайшего макета |
| `.mdx` | всегда | Vite, с React или Preact | компонентным маршрутом |
| `.tsx` | `useFF` — это React, Solid или Preact | Vite и структура | — компонентный маршрут |
| `.vue` | `useFF` является Vue | Vite и Vue | составным маршрутом |
| `.svelte` | `useFF` является Svelte | Vite и Svelte | составным маршрутом |
| `.py` | всегда | Python | обработчик API: `GET`, `POST`, ... это методы |

Файл, расширение которого неактивно, пропускается с предупреждением и не обслуживается. В клиентском режиме `.nexy` отклоняется до запуска сервера. См. [Соглашения о файлах](../reference/file-conventions.md).

## Жизненный цикл рендеринга

Три вопроса решают все, что замечает читатель:

| Вопрос | Ответ | Страница |
|---|---|---|
| Кто создает HTML? | сервер или браузер для клиентского маршрута | [Рендеринг](../rendering/README.md) |
| Когда данные читаются? | при каждом запросе, при каждой регенерации или в браузере | [SSR](../rendering/ssr.md), [ISR](../rendering/isr.md) |
| Когда прибудет JavaScript? | только для острова или для всего документа | [Острова](../rendering/islands.md), [CSR](../rendering/csr.md) |

В режиме сервера сервер отображает каждую страницу, `revalidate` кэширует одну страницу на каждый URL-адрес, а острова добавляют JavaScript к одному компоненту. В клиентском режиме первый документ отображается в Node, а затем навигация происходит в браузере.

`__nexy__/` содержит все сгенерированное: скомпилированные страницы, запись клиента, выходные данные сборки. Никогда не редактируйте его, никогда не фиксируйте его; удалите его, чтобы выполнить чистую сборку.

## Интеграция с интерфейсом

**Vite не заменяет Nexy.** Vite объединяет и обслуживает клиентский код. Он не маршрутизирует запрос, не отображает страницу `.nexy`, не запускает действие и не владеет источником. Браузер обращается к одному источнику — Nexy — и в разработке Nexy проксирует конечные точки Vite через него, поэтому нет необходимости настраивать CORS.

**Nexy не заменяет React.** Nexy решает, какой компонент рендерится, когда и с какими реквизитами; фреймворк владеет моделью компонентов, реактивностью и экосистемой. Страница `.nexy` импортирует компонент как остров; в режиме клиента маршрут *является* компонентом.

Для компонентного маршрута Python записывает только тонкий модуль-оболочку, указывающий на файл. Компиляция и рендеринг на стороне сервера — работа Vite.

## Разработка и производство

| | `nx dev` | `nx build` затем `nx start` |
|---|---|---|
| Страницы | компилируются при сохранении | компилируются один раз заранее |
| Клиентский код | Vite сервер разработки с горячей перезагрузкой, собственный пакет Nexy | в `__nexy__/client/`, предварительно обработанный HTML |
| Node.js | работает рядом с Python | и не требуется для обслуживания |
| Ошибки | наложение в браузере, панель инструментов на каждой странице | страницы статуса без подробностей |
| Исходный | один порт, `3000` | один порт |

Что не меняется: те же правила маршрутизации, те же файлы подкачки, те же `nexyconfig.py`. Страница, которая ведет себя по-разному, является ошибкой, а не режимом.
