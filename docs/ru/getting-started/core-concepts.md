# Основные понятия

Ментальная модель до API: четыре уровня чтения, затем понятия, которые возвращаются на каждой странице. Каждое понятие здесь занимает одну строку и ссылку на более глубокую страницу.

## Как читать эти документы

| Уровень | Вопрос, на который он отвечает | Начните с |
|---|---|---|
| Архитектура приложения | какой уровень отвечает на запрос и что он отказывается делать | [Архитектура](../architecture.md) |
| Структура приложения | где находится код и каким становится файл | [Структура проекта](project-structure.md) |
| Презентация и рендеринг | того, что видит читатель, и кто создает HTML | [Просмотры](../views/README.md), [Рендеринг](../rendering/README.md) |
| Взаимодействие с приложением | что делает читатель и что запускается в ответ | [Действия](../guides/actions.md) |

Уровни читаются в таком порядке один раз. После этого вам нужна страница — это справочник, а не курс.

## Архитектура приложения

Три способа решить, какой код соответствует URL-адресу. Это альтернативы, а не слои:

- **Маршрутизация на основе файлов (FBR)**: файл в папке `src/routes/` является маршрутом. Значение по умолчанию.
- **Модульный маршрутизатор**: контроллеры и модули из `src/apps/`, объявленные с помощью декораторов, для кодовой базы в стиле NestJS.
- **Пользовательский маршрутизатор**: существующий FastAPI `APIRouter` включенный в приложение.

Выбор одного из трех – это одно решение. Выбор внешнего интерфейса — это еще один отдельный вопрос: см. [Выбор маршрутизатора](../routing/README.md) и [Просмотры](../views/README.md)].

## Структура приложения

Пять понятий, которые читатель из Next.js обычно сливает в одно. Это не одно и то же, и разница объясняет большинство вопросов «почему моя страница не отображается».

| Понятие | Что это такое | Чем это не является |
|---|---|---|
| **Маршрут** | шаблон URL-адреса, созданный по пути к файлу | файл: один файл может отвечать на несколько URL-адресов (`[slug]`) |
| **Page** | файл маршрута, который отображает представление: `.nexy`, `.md`, `.mdx`, `.tsx`, `.vue`, `.svelte` | конечная точка: он отвечает на документ, а не на данные |
| **Просмотр** | того, что создает тело страницы: Jinja2 и Python, Markdown или клиентский компонент | маршрут: одно и то же представление может обслуживать несколько страниц |
| **Компонент** | повторно используемый фрагмент страница импортирует | маршрут: в режиме сервера компонент никогда не обслуживается сам по себе |
| **Обработчик маршрута** | функция файла маршрута `.py`, названная в честь метода HTTP (`GET`, `POST`, …) | страница: она возвращает JSON, файл или `Response` |
| **Конечная точка** | пара (URL, метод), на которую отвечает обработчик | обработчик: один файл может отвечать нескольким конечным точкам |

В одном предложении: **страница — это файл маршрута, представление — это то, что ее отображает, компонент — это то, что страница повторно использует, обработчик отвечает конечной точке.**

Еще два слова, которые повторяются повсюду:

- **Layout**: файл `layout.*`, который оборачивает страницы под своей папкой; корневой владеет HTML-документом. См. [Макеты](../routing/fbr/layouts/README.md).
- **Зависимость**: функция, которая запускается перед обработчиком, применяется для каждого маршрута или для каждой папки. См. [Зависимости](../routing/fbr/dependencies/README.md).

## Презентация и рендеринг

Два независимых решения, которые часто путают:

- **Формат** определяет, какой файл отображает страницу: [Views](../views/README.md).
- **Режим** решает, кто и когда создает HTML: [Рендеринг](../rendering/README.md).

| Понятие | Одна строка |
|---|---|
| Режим сервера | сервер отображает страницы `.nexy` и `.md`; компоненты являются островами ([режимы](../routing/fbr/modes.md)) |
| Клиентский режим | `useCSR = True`: файлы фреймворка являются маршрутами, а навигация происходит в браузере |
| SSR, ISR, CSR, острова | четыре режима рендеринга, определяемые для каждой страницы, кроме CSR, который устанавливается для каждого проекта ([рендеринг](../rendering/README.md)) |
| Гидратация | браузер, прикрепляющий фреймворк к уже отправленному сервером HTML ([острова](../rendering/islands.md)) |
| Реквизит | значения, которые родитель передает компоненту, объявленному `name: prop[type]` в файле `.nexy` ([.nexy files](../views/nexy/README.md)) |

## Взаимодействие с приложением

| Понятие | Одна строка |
|---|---|
| Действие | функция Python с пометкой `@Action`, служащая как `POST`, вызываемая из формы или как типизированная функция ([actions](../guides/actions.md)) |
| Сформируйте | HTML-форму, которая отправляет сообщение в действие, при этом ошибки проверки возвращаются на страницу ([actions](../guides/actions.md)) |
| Навигационные | ссылки с предварительной выборкой и перехватчики, считывающие путь, запрос, файлы cookie и сеанс ([крючки](../routing/fbr/navigation/hooks.md)) |
| Извлечение данных | выполняется страницей или обработчиком, которому это необходимо; Nexy не поставляет уровень клиентских данных ([handlers](../routing/fbr/handlers/README.md)) |

## Чего Nexy не делает

Аутентификация, авторизация, база данных, интернационализация, фоновые задания, электронная почта, платежи и поиск — это **ответственность вашего приложения**, а не фреймворка. Nexy дает точки расширения и говорит, куда подключить каждую: см. [границы](../architecture.md#boundaries).

Причина не в минимализме как таковом: фреймворк, который выбирает ваш ORM или вашу библиотеку аутентификации, решил что-то, что может решить только ваше приложение.
