# كيف يعمل نيكسي

النموذج العقلي في صفحة واحدة: ما يبنيه Nexy، وما يبنيه Vite، وما يحدث بين ملف وصفحة في متصفحك. اقرأها مرة واحدة؛ بقية الوثائق هي بعد ذلك مجموعة من التفاصيل.

## العمارة نيكسي

يعبر الطلب خمس طبقات: Uvicorn يقبله، وتزينه البرامج الوسيطة، ويختار جهاز التوجيه ملفًا، ويحول العارض هذا الملف إلى HTML أو JSON، وتتولى طبقة العميل المسؤولية إذا كانت الصفحة تحتوي على JavaScript. تمتلك Nexy الثلاثة الأوسط. Vite والإطار الخاص بك يمتلك العميل؛ يمتلك تطبيقك البيانات والمصادقة والترخيص.

كل طبقة، وما ترفض القيام به، موجود في [العمارة](../architecture.md). للحصول على حزم Nexy نفسها، راجع `ARCHITECTURE.md` في جذر المستودع - وهو مكتوب للمساهمين.

## دورة حياة التطبيق

`nx dev` يفعل ستة أشياء قبل الطلب الأول:

1. يتحقق من صحة `nexyconfig.py`، ويتوقف عند تكوين غير صالح؛
2. يضمن أن حزم Python المشروع قابلة للاستيراد؛
3. يحل المنافذ، ويحذف العلامة `__nexy__/nexy.prod` التي لا معنى لها؛
4. ينشئ ملفات العميل ويجمع المسارات بالتوازي؛
5. يبدأ Vite وينتظر حتى يجيب؛
6. يقوم بتثبيت مراقب الملفات، ثم يسمح لـ uvicorn باستيراد `nexy.modules.routers.app:_server`.

يقوم هذا الاستيراد بتجميع التطبيق - البرامج الوسيطة، والإجراءات، وأجهزة التوجيه، ومعالجات الأخطاء - ويتم تقديم الطلب الأول من خلال هذا التجميع. عند الحفظ، يقوم المراقب بإعادة تشغيل uvicorn؛ الصفحة التي ظهرت أو اختفت أو تم نقلها تعمل أيضًا على إعادة إنشاء قائمة مسارات العميل.

## نظام التوجيه

يصبح المسار الموجود ضمن `src/routes/` عنوان URL من خلال أربع قواعد:

| الملف | عنوان URL |
|---|---|
| `blog/index.nexy` | `/blog` |
| `blog/[slug].nexy` | `/blog/hello` |
| `blog/[...parts].nexy` | `/blog/a/b` |
| `(marketing)/about.nexy` | `/about` |

لا يظهر الامتداد مطلقًا؛ `index` هو مسار المجلد الخاص به؛ مجلد بين قوسين يجمع الملفات دون إضافة مقطع.

عندما يتمكن شيئين من الإجابة على نفس عنوان URL، **أول واحد مسجل يفوز**، ويسجل Nexy دائمًا بهذا الترتيب:

1. نقطة نهاية الإجراءات؛
2. الملفات الثابتة: `/public`، `/assets`، `/favicon.ico`؛
3. معياري `APIRouter` (`useRouter`)؛
4. مسارات الملفات، الأكثر تحديدًا أولاً: المسارات الثابتة، ثم المسارات الديناميكية ذات المقاطع الأكثر ثباتًا، ثم رسائل التقاط الرسائل الخاطئة.

يتم تسجيل مسارين للملفات متساويين في الخصوصية بترتيب المسار الأبجدي، لذلك يجيب `[id].nexy` قبل `[slug].nexy`. وبالتالي فإن المسار المعياري يتفوق على الصفحة التي لها نفس المسار. هذا هو ترتيب الأسبقية الذي يمكنك الاعتماد عليه، وليس قاعدة فاصلة للعب بها: أعط عنوان URL واحدًا وملفًا واحدًا.

## نظام المشاهدة

يحدد امتداد الملف ما هو عليه، ويقرر تكوين المشروع الامتدادات النشطة.

| الامتداد | نشط عندما تم تجميع | بواسطة | بمثابة |
|---|---|---|---|
| `.nexy` | وضع الخادم | Nexy: تصبح المادة الأمامية Python، ويصبح الترميز Jinja2 | صفحة |
| `.md` | دائمًا | Nexy: نكهة GitHub Markdown، معرفات العناوين، جدول المحتويات | صفحة، داخل أقرب تخطيط |
| `.mdx` | دائمًا | Vite، مع React أو Preact | مسار مكون |
| `.tsx` | `useFF` هو React، Solid أو Preact | Vite والإطار | مسار مكون |
| `.vue` | `useFF` هو Vue | Vite و Vue | مسار مكون |
| `.svelte` | `useFF` هو Svelte | Vite و Svelte | مسار مكون |
| `.py` | دائمًا | Python | معالج API: `GET`، `POST`، ... هي الطرق |

يتم تخطي الملف الذي لا يكون امتداده نشطًا مع تحذير، ولا يتم عرضه. في وضع العميل، يتم رفض `.nexy` قبل بدء تشغيل الخادم. انظر [اصطلاحات الملفات](../reference/file-conventions.md).

## دورة حياة العرض

ثلاثة أسئلة تقرر كل ما يلاحظه القارئ:

| سؤال | الجواب | الصفحة |
|---|---|---|
| من ينتج HTML؟ | الخادم، أو المتصفح لمسار العميل | [العرض](../rendering/README.md) |
| متى تتم قراءة البيانات؟ | في كل طلب، في كل تجديد، أو في المتصفح | [SSR](../rendering/ssr.md)، [ISR](../rendering/isr.md) |
| متى يصل JavaScript؟ | فقط لجزيرة، أو للوثيقة بأكملها | [الجزر](../rendering/islands.md)، [CSR](../rendering/csr.md) |

في وضع الخادم، يعرض الخادم كل صفحة، ويخزن `revalidate` صفحة واحدة مؤقتًا لكل عنوان URL، وتضيف الجزر JavaScript إلى مكون واحد. في وضع العميل، يتم عرض المستند الأول في Node ثم يتم التنقل في المتصفح.

`__nexy__/` يحمل كل ما تم إنشاؤه: الصفحات المجمعة، وإدخال العميل، ومخرجات البناء. لا تقم بتحريره أبدًا، ولا تلتزم به أبدًا؛ احذفه لفرض بناء نظيف.

## تكامل الواجهة الأمامية

**Vite لا يحل محل Nexy.** Vite يجمع ويخدم كود العميل. لا يقوم بتوجيه طلب أو عرض صفحة `.nexy` أو تشغيل إجراء أو امتلاك الأصل. يتحدث المتصفح إلى أصل واحد - Nexy's - وفي تطوير نقاط نهاية وكلاء Nexy Vite من خلاله، لذلك لا يوجد CORS لتكوينه.

**Nexy لا يحل محل React.** Nexy هو الذي يقرر أي مكون سيتم عرضه، ومتى، وبأي دعم؛ يمتلك الإطار النموذج المكون والتفاعل والنظام البيئي. تستورد صفحة `.nexy` مكونًا كجزيرة؛ في وضع العميل، يكون المسار مكونًا.

بالنسبة لمسار المكون، يكتب Python فقط وحدة مجمعة رفيعة تشير إلى الملف. التجميع والعرض من جانب الخادم هما مهمة Vite.

## التطوير والإنتاج

| | `nx dev` | `nx build` ثم `nx start` |
|---|---|---|
| الصفحات | التي تم تجميعها عند حفظ | تم تجميعها مرة واحدة، في وقت مبكر |
| رمز العميل | Vite خادم التطوير مع إعادة التحميل السريع، خلف حزمة Nexy الأصلية | في `__nexy__/client/`، HTML المعروض مسبقًا |
| Node.js | يجري بجانب Python | لا حاجة للخدمة |
| أخطاء | متراكبة في المتصفح، شريط الأدوات في كل صفحة | صفحات الحالة بدون تفاصيل |
| الأصل | منفذ واحد، `3000` | منفذ واحد |

ما لا يتغير: نفس قواعد التوجيه، نفس ملفات الصفحات، نفس `nexyconfig.py`. الصفحة التي تتصرف بشكل مختلف بين الاثنين هي خطأ وليست وضعًا.
