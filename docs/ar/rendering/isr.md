# ISR (لا معنى لها أثناء إعادة التحقق)

## التعريف

يقوم ISR بتخزين HTML لصفحة واحدة مؤقتًا، لكل عنوان URL، ويعرضه حتى تنتهي نافذته. لا يزال يتم عرض النسخة منتهية الصلاحية بينما يتم عرض نسخة جديدة في الخلفية: أي *stale-while-revalidate*.

## كيف يعمل

`revalidate = N` في الجزء الأمامي من صفحة `.nexy` يتم تشغيله. `N` هو عدد الثواني؛ تعني القيمة المفقودة أو الصفرية أو السلبية عدم وجود ذاكرة تخزين مؤقت على الإطلاق.

مفتاح ذاكرة التخزين المؤقت هو **مسار الطلب فقط** - `request.scope["path"]`. سلسلة الاستعلام ليست جزءًا منها.

| ماذا | القيمة |
|---|---|
| مفتاح | مسار URL (`/blog/hello`) |
| التخزين | محدد بواسطة `useISRCache`: الذاكرة افتراضيًا أو الملف أو Redis أو المتجر المخصص |
| ملزمة | 256 إدخالاً لمخزن الذاكرة، الأقل استخدامًا تم إخلاؤها مؤخرًا؛ file وRedis يحتفظان بالإدخالات حتى يتم إبطالها |
| رأس الاستجابة | `cache-control: public, s-maxage=N, stale-while-revalidate=N` |

تحمل كل استجابة ISR هذا الرأس، بما في ذلك العرض الأول والعرض الاحتياطي عندما يكون المتجر معطلاً. يمكن أن تستخدمه شبكة CDN للاحتفاظ بنسختها الخاصة من نفس عنوان URL العام.

## تقديم دورة الحياة

1. يصل طلب لصفحة تعلن `revalidate`.
2. لم يتم الإدخال بعد: يتم عرض الصفحة وتخزينها وإعادتها.
3. إدخال أصغر من `N` ثانية: يتم إرجاعه كما هو، ولا يتم عرض الصفحة.
4. إدخال أقدم من `N` ثانية: يتم إرجاع الإدخال **الذي لا معنى له** على الفور، وتعرض مهمة الخلفية إدخالاً جديدًا.
5. إذا فشل عرض الخلفية هذا، فسيظل الإدخال القديم وسيحاول الطلب القديم التالي مرة أخرى.
6. إذا فشل المخزن، فسيتم عرض الصفحة وإرجاعها بدون إدخال مخبأ. لا يزال الطلب ينجح.

## متى تستخدم

- نفس HTML لكل زائر: منشور مدونة، صفحة منتج، صفحة توثيق.
- تتم قراءة الصفحة كثيرًا ونادرًا ما تتغير.
- يمكن أن يكون عمر البيانات بضع ثوانٍ دون أن يلاحظها أحد.

## التكوين

```nexy filename="src/routes/blog/index.nexy"
---
revalidate = 60
---
<h1>Rendered at most once per minute</h1>
```

`N` هو عدد صحيح عادي. لا يوجد تجاوز لكل مسار في أي مكان آخر، ومعالجات `.py` ليست صفحات: فهي لا تدخل أبدًا إلى ذاكرة التخزين المؤقت هذه.

## اختر متجرا

تعيين `useISRCache` في `nexyconfig.py`:

```python filename="nexyconfig.py"
from nexy.core.models import NexyConfigModel


class NexyConfig(NexyConfigModel):
    useISRCache = "file"
```

| القيمة | متجر | تمت مشاركته بواسطة |
|---|---|---|
| غير مضبوط، `None`، أو `"memory"` | ذاكرة العملية، يحدها 256 إدخالات | عامل واحد |
| `"file"` | ملفات JSON في `.nexy/isr` | العمال على مضيف واحد |
| `{"type": "file", "directory": ".cache/isr"}` | ملفات JSON في الدليل المحدد | العمال على مضيف واحد |
| `"redis"` | ريديس في `redis://localhost:6379/0` | أي عامل يصل إلى الخادم |
| `{"type": "redis", "url": "redis://cache:6379/0"}` | Redis على عنوان URL هذا | أي عامل يصل إلى الخادم |
| `{"type": "redis", "client": client}` | عميل Redis الذي تمر به | أي عامل يصل إلى الخادم |
| كائن مع `get`، `set` و `invalidate` | متجرك الخاص | مهما كان سهمه |

يحتاج متجر Redis إلى حزمة العميل: `uv add redis`. لم يتم تثبيته مع Nexy. يقوم المتجر المخصص بتنفيذ البروتوكول `ISRCache` من `nexy.modules.runtime.cache`؛ `get` يُرجع `CacheEntry` أو `None`.

تتم كتابة إدخالات الملف بشكل ذري، لذلك لا يقرأ العامل أبدًا صفحة نصف مكتوبة. يقرأ العمال الذين يستخدمون نفس الدليل أو نفس خادم Redis نفس الإدخال. المتجر المعطل لا يكلف سوى عرضًا: فهو لا يجيب أبدًا على الطلب بخطأ.

## مثال

منشور مدونة يقرأ قاعدة بيانات:

```nexy filename="src/routes/blog/[slug].nexy"
---
revalidate = 300
slug: prop[str] = "untitled"
posts = {"hello": {"title": "Hello"}, "other": {"title": "Other"}}
post = posts.get(slug, {"title": "Untitled"})
---
<h1>{{ post.title }}</h1>
```

الطلب الأول إلى `/blog/hello` العروض والمخازن. يتم تقديم الـ 300 ثانية التالية من المتجر المحدد. `/blog/other` هو إدخال منفصل، يتم تقديمه وتخزينه بمفرده. في المشروع الحقيقي `posts` يأتي من قاعدة بيانات أو خدمة، يتم استدعاؤها مرة واحدة في كل عملية تجديد.

## ما يمكن لـ CDN مشاركته وما لا يمكنه مشاركته

يمكن لـ CDN الذي يحترم `cache-control` الاحتفاظ بنسخة واحدة من `/blog/hello` لمدة `s-maxage` ثانية وتقديمها أثناء إعادة التحقق من صحتها. ويتقاسم تلك النسخة بين الزائرين والعاملين لأن الرد يقول `public`.

لا يعرف CDN متجر Nexy. `revalidate()` في [الإجراء](../guides/actions.md) يزيل الإدخال من متجر Nexy الذي تم تكوينه، لكنه لا يقوم بإزالة CDN. تحتفظ شبكة CDN بنسختها حتى تنتهي النافذة الخاصة بها، أو حتى تقوم بتكوين عملية التطهير الخاصة بها.

لا تمنح CDN صفحة يعتمد HTML فيها على الزائر. يقول الرد `public`، ومفتاح Nexy هو المسار وحده: سلسلتا استعلام على مسار واحد تشتركان في إدخال واحد. يمكن تقديم جلسة أو ملف تعريف ارتباط أو معرف مستخدم بتنسيق HTML لزائر آخر.

## القيود

**يضمن Nexy** أن مفتاح ذاكرة التخزين المؤقت هو المسار، ويتم تقديم النسخة القديمة أثناء التجديد، ويعود فشل المتجر إلى العرض.

**وفقًا للاتفاقية**، فإن الصفحة التي تعلن أن `revalidate` هي محتوى عام. اكتبه كما لو أن كل زائر يرى نفس HTML.

**تطبيقك مسؤول عن** كل شيء آخر:

| الحد | ماذا يعني |
|---|---|
| تم تجاهل سلسلة الاستعلام | `/search?q=a` و `/search?q=b` يشتركان في مدخل واحد. لا تقم بتخزين صفحة بحث مؤقتًا. |
| الجلسة ليست معزولة | الرد يقول `public`، ويتم تقديم HTML الخاص بالزائر الأول للجميع. لا تقرأ الجلسة أبدًا في صفحة بها `revalidate`. |
| لم يتم مسح CDN | `revalidate()` يقوم بتطهير متجر Nexy، وليس CDN أو وكيل آخر أمامه. |
| لا يوجد TTL في الملفات ومتاجر Redis | تبقى الإدخالات حتى `revalidate()` أو تقوم عملية التنظيف الخاصة بك بإزالتها. يقوم مخزن الذاكرة بطرد الإدخال الأقل استخدامًا مؤخرًا بعد 256. |
| التجديدات المتزامنة | لا شيء يزيل تكرارها: يمكن لعشرة طلبات قديمة أن تبدأ عشرة عمليات عرض. |
| الأخطاء صامتة | تستمر عملية التجديد أو التخزين الفاشلة في خدمة الصفحة؛ لا يتم إرجاع الفشل. |
