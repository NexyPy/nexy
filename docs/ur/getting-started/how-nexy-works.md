# Nexy کیسے کام کرتا ہے۔

ایک صفحہ میں ذہنی ماڈل: Nexy کیا بناتا ہے، کیا Vite بناتا ہے، اور آپ کے براؤزر میں ایک فائل اور صفحہ کے درمیان کیا ہوتا ہے۔ ایک بار پڑھیں؛ باقی دستاویزات پھر تفصیلات کا ایک سیٹ ہے۔

## Nexy فن تعمیر

ایک درخواست پانچ پرتوں کو عبور کرتی ہے: Uvicorn اسے قبول کرتا ہے، مڈل ویئر اسے سجاتا ہے، روٹر ایک فائل چنتا ہے، پیش کنندہ اس فائل کو HTML یا JSON میں بدل دیتا ہے، اور اگر صفحہ میں JavaScript ہے تو کلائنٹ کی پرت سنبھال لیتی ہے۔ Nexy درمیانی تین کا مالک ہے۔ Vite اور آپ کا فریم ورک کلائنٹ کا مالک ہے۔ آپ کی درخواست ڈیٹا، تصدیق اور اجازت کی مالک ہے۔

ہر پرت، اور جو کچھ کرنے سے انکار کرتی ہے، وہ [آرکیٹیکچر](../architecture.md) میں ہے۔ خود Nexy کے پیکجز کے لیے، ریپوزٹری روٹ پر `ARCHITECTURE.md` دیکھیں - یہ شراکت داروں کے لیے لکھا گیا ہے۔

## ایپلی کیشن لائف سائیکل

`nx dev` پہلی درخواست سے پہلے چھ کام کرتا ہے:

1. توثیق کرتا ہے `nexyconfig.py`، اور ایک غلط ترتیب پر رک جاتا ہے۔
2. اس بات کو یقینی بناتا ہے کہ پروجیکٹ کے Python پیکجز قابل درآمد ہیں۔
3. بندرگاہوں کو حل کرتا ہے، اور باسی `__nexy__/nexy.prod` مارکر کو حذف کرتا ہے۔
4. کلائنٹ فائلیں تیار کرتا ہے اور روٹس کو متوازی طور پر مرتب کرتا ہے۔
5. شروع ہوتا ہے Vite اور اس کا جواب آنے تک انتظار کرتا ہے۔
6. فائل واچر انسٹال کرتا ہے، پھر یوویکورن کو درآمد کرنے دیتا ہے `nexy.modules.routers.app:_server`۔

وہ درآمد ایپلیکیشن کو جمع کرتی ہے - مڈل ویئر، ایکشنز، روٹرز، ایرر ہینڈلرز - اور پہلی درخواست اس اسمبلی کے ذریعہ پیش کی جاتی ہے۔ جب آپ بچت کرتے ہیں تو نگہبان یووی کارن کو دوبارہ شروع کرتا ہے۔ ایک صفحہ جو ظاہر، غائب یا منتقل ہو گیا ہے وہ کلائنٹ روٹ لسٹ کو بھی دوبارہ تخلیق کرتا ہے۔

## روٹنگ سسٹم

`src/routes/` کے تحت راستہ چار اصولوں سے یو آر ایل بن جاتا ہے۔

| فائل | URL |
|---|---|
| `blog/index.nexy` | `/blog` |
| `blog/[slug].nexy` | `/blog/hello` |
| `blog/[...parts].nexy` | `/blog/a/b` |
| `(marketing)/about.nexy` | `/about` |

توسیع کبھی ظاہر نہیں ہوتی؛ `index` اس کے فولڈر کا روٹ ہے۔ قوسین میں ایک فولڈر سیگمنٹ کو شامل کیے بغیر فائلوں کو گروپ کرتا ہے۔

جب دو چیزیں ایک ہی URL کا جواب دے سکتی ہیں، **پہلا رجسٹرڈ جیتتا ہے**، اور Nexy ہمیشہ اس ترتیب میں رجسٹر ہوتا ہے:

1. اعمال کا اختتامی نقطہ؛
2. جامد فائلیں: `/public`، `/assets`، `/favicon.ico`؛
3. ایک ماڈیولر `APIRouter` (`useRouter`)؛
4. فائل روٹس، سب سے پہلے سب سے مخصوص: جامد راستے، پھر سب سے زیادہ مقررہ حصوں کے ساتھ متحرک راستے، پھر کیچ-آل۔

مساوی خصوصیت کے دو فائل روٹس حروف تہجی کے راستے کی ترتیب میں رجسٹرڈ ہیں، لہذا `[id].nexy` جواب `[slug].nexy` سے پہلے۔ اس لیے ایک ماڈیولر روٹ اسی راستے کے ساتھ ایک صفحہ کو مات دیتا ہے۔ یہ ایک ترجیحی آرڈر ہے جس پر آپ بھروسہ کر سکتے ہیں، نہ کہ ٹائی بریک کے اصول کے ساتھ کھیلنے کے لیے: ایک URL ایک فائل دیں۔

## دیکھنے کا نظام

فائل کی توسیع فیصلہ کرتی ہے کہ یہ کیا ہے، اور پروجیکٹ کی تشکیل فیصلہ کرتی ہے کہ کون سی ایکسٹینشن فعال ہیں۔

| توسیع | فعال جب | مرتب کی گئی | بطور |
|---|---|---|---|
| `.nexy` | سرور موڈ | Nexy: فرنٹ میٹر بن جاتا ہے Python، مارک اپ بن جاتا ہے Jinja2 | ایک صفحہ |
| `.md` | ہمیشہ | Nexy: GitHub-flavored Markdown، heading ids، Table of content | ایک صفحہ، قریب ترین لے آؤٹ کے اندر |
| `.mdx` | ہمیشہ | Vite، React یا Preact | ایک جزو کا راستہ |
| `.tsx` | `useFF` ہے React، Solid یا Preact | Vite اور فریم ورک | ایک جزو کا راستہ |
| `.vue` | `useFF` ہے Vue | Vite اور Vue | ایک جزوی راستہ |
| `.svelte` | `useFF` ہے Svelte | Vite اور Svelte | ایک جزوی راستہ |
| `.py` | ہمیشہ | Python | ایک API ہینڈلر: `GET`، `POST`، ... طریقے ہیں |

ایک فائل جس کی ایکسٹینشن فعال نہیں ہے اسے وارننگ کے ساتھ چھوڑ دیا جاتا ہے، پیش نہیں کیا جاتا۔ کلائنٹ موڈ میں، سرور شروع ہونے سے پہلے `.nexy` کو مسترد کر دیا جاتا ہے۔ دیکھیں [فائل کنونشنز](../reference/file-conventions.md)۔

## رینڈرنگ لائف سائیکل

تین سوالات ہر چیز کا فیصلہ کرتے ہیں جو ایک قارئین کو نوٹس دیتا ہے:

| سوال | جواب | صفحہ |
|---|---|---|
| HTML کون تیار کرتا ہے؟ | سرور، یا کلائنٹ روٹ کے لیے براؤزر | [رینڈرنگ](../rendering/README.md) |
| ڈیٹا کب پڑھا جاتا ہے؟ | ہر درخواست پر، ہر تخلیق نو پر، یا براؤزر میں | [SSR](../rendering/ssr.md)، [ISR](../rendering/isr.md) |
| JavaScript کب آئے گا؟ | صرف ایک جزیرے کے لیے، یا پوری دستاویز کے لیے | [جزیرے](../rendering/islands.md)، [CSR](../rendering/csr.md) |

سرور موڈ میں سرور ہر صفحہ کو رینڈر کرتا ہے، `revalidate` فی یو آر ایل ایک صفحہ کیش کرتا ہے، اور جزیرے JavaScript کو ایک جز میں شامل کرتے ہیں۔ کلائنٹ موڈ میں پہلی دستاویز نوڈ اور نیویگیشن میں پیش کی جاتی ہے پھر براؤزر میں ہوتی ہے۔

`__nexy__/` پیدا ہونے والی ہر چیز کو رکھتا ہے: مرتب شدہ صفحات، کلائنٹ کا اندراج، تعمیراتی آؤٹ پٹ۔ اس میں کبھی ترمیم نہ کریں، اس کا ارتکاب نہ کریں۔ صاف تعمیر پر مجبور کرنے کے لیے اسے حذف کریں۔

## فرنٹ اینڈ انضمام

**Vite کی جگہ نہیں لیتا Nexy** Vite بنڈل اور کلائنٹ کوڈ پیش کرتا ہے۔ یہ کسی درخواست کو روٹ نہیں کرتا، ایک `.nexy` صفحہ پیش کرتا ہے، ایکشن چلاتا ہے یا اصل کا مالک نہیں ہوتا ہے۔ براؤزر ایک اصل سے بات کرتا ہے - Nexy's - اور ترقی میں Nexy proxies Vite کے اختتامی نقطہ اس کے ذریعے ہے، لہذا ترتیب دینے کے لیے کوئی CORS نہیں ہے۔

**Nexy کی جگہ نہیں لیتا React.** Nexy فیصلہ کرتا ہے کہ کون سا جزو رینڈر کرتا ہے، کب، اور کس پرپس کے ساتھ؛ فریم ورک جزو ماڈل، رد عمل اور ماحولیاتی نظام کا مالک ہے۔ ایک `.nexy` صفحہ جزیرے کے طور پر جز کو درآمد کرتا ہے۔ کلائنٹ موڈ میں ایک راستہ *ایک جزو ہے*۔

ایک جزو کے راستے کے لیے، Python صرف ایک پتلی ریپر ماڈیول لکھتا ہے جو فائل کی طرف اشارہ کرتا ہے۔ تالیف اور سرور سائیڈ رینڈرنگ Vite کا کام ہے۔

## ترقی اور پیداوار

| | `nx dev` | `nx build` پھر `nx start` |
|---|---|---|
| جب آپ محفوظ کرتے ہیں تو صفحات | مرتب کیے جاتے ہیں | ایک بار مرتب کیے جاتے ہیں، وقت سے پہلے |
| کلائنٹ کوڈ | Vite گرم دوبارہ لوڈ کے ساتھ دیو سرور، Nexy کی اپنی اصلیت کے پیچھے | بنڈل `__nexy__/client/` میں، پہلے سے پیش کردہ HTML |
| Node.js | Python کے آگے چلتا ہے۔ | خدمت کرنے کی ضرورت نہیں |
| براؤزر میں خرابیاں | اوورلے، ہر صفحے پر ٹول بار | اسٹیٹس پیجز بغیر تفصیلات کے |
| اصل | ایک بندرگاہ، `3000` | ایک بندرگاہ |

کیا تبدیل نہیں ہوتا: وہی روٹنگ کے اصول، وہی صفحہ فائلیں، وہی `nexyconfig.py`۔ ایک صفحہ جو دونوں کے درمیان مختلف طریقے سے برتاؤ کرتا ہے وہ ایک بگ ہے، موڈ نہیں۔
