# بنیادی تصورات

ذہنی ماڈل، API سے پہلے: پڑھنے کے چار درجے، پھر تصورات جو ہر صفحے پر واپس آتے ہیں۔ ہر تصور کو یہاں ایک لائن ملتی ہے اور اس صفحہ کا ایک لنک جو گہرا جاتا ہے۔

## ان دستاویزات کو کیسے پڑھیں

| سطح | اس سوال کا جواب | | سے شروع کریں
|---|---|---|
| ایپلیکیشن آرکیٹیکچر | کون سی پرت کسی درخواست کا جواب دیتی ہے، اور کیا کرنے سے انکار کرتی ہے | [آرکیٹیکچر](../architecture.md) |
| درخواست کا ڈھانچہ | جہاں کوڈ رہتا ہے، اور فائل کیا بنتی ہے | [پروجیکٹ ڈھانچہ](project-structure.md) |
| پریزنٹیشن اور رینڈرنگ | جو قاری دیکھتا ہے، اور HTML کون تیار کرتا ہے | [دیکھے](../views/README.md)، [رینڈرنگ](../rendering/README.md) |
| درخواست کا تعامل | قاری کیا کرتا ہے، اور جواب میں کیا چلتا ہے | [اعمال](../guides/actions.md) |

سطحوں کو اس ترتیب میں ایک بار پڑھا جاتا ہے۔ اس کے بعد، آپ کو جس صفحہ کی ضرورت ہے وہ ایک تلاش ہے، نہ کہ کورس۔

## ایپلیکیشن فن تعمیر

یہ فیصلہ کرنے کے تین طریقے کہ کون سا کوڈ یو آر ایل کا جواب دیتا ہے۔ وہ متبادل ہیں، پرتیں نہیں:

- **فائل پر مبنی روٹنگ (FBR)**: `src/routes/` کے تحت فائل ایک روٹ ہے۔ پہلے سے طے شدہ۔
- **ماڈیولر راؤٹر**: NestJS طرز کے کوڈ بیس کے لیے `src/apps/` کے تحت کنٹرولرز اور ماڈیولز، ڈیکوریٹرز کے ساتھ اعلان کردہ۔
- **کسٹم راؤٹر**: ایک موجودہ FastAPI `APIRouter` ایپلی کیشن میں شامل ہے۔

تین میں سے کسی ایک کا انتخاب کرنا ایک فیصلہ ہے۔ فرنٹ اینڈ فریم ورک کا انتخاب ایک اور ہے، الگ الگ: دیکھیں [روٹر کا انتخاب کریں](../routing/README.md) اور [دیکھے](../views/README.md)۔

## درخواست کا ڈھانچہ

پانچ تصورات جو کہ Next.js سے آنے والا قاری عموماً ایک میں ضم ہوجاتا ہے۔ وہ ایک ہی چیز نہیں ہیں، اور فرق زیادہ تر سوالات کی وضاحت کرتا ہے "میرا صفحہ کیوں پیش نہیں کر رہا ہے"۔

| تصور | یہ کیا ہے | یہ کیا نہیں ہے |
|---|---|---|
| **روٹ** | ایک URL پیٹرن، جو ایک فائل | ایک فائل کے راستے سے تیار ہوتا ہے: ایک فائل کئی یو آر ایل کا جواب دے سکتی ہے (`[slug]`) |
| **صفحہ** | ایک روٹ فائل جو ایک منظر پیش کرتی ہے: `.nexy`، `.md`، `.mdx`، `.tsx`، `.vue`، `.svelte` | ایک اختتامی نقطہ: یہ ایک دستاویز کا جواب دیتا ہے، ڈیٹا نہیں |
| **دیکھیں** | ایک صفحہ کا جسم کیا پیدا کرتا ہے: Jinja2 اور Python، Markdown، یا کلائنٹ کا ایک جزو | ایک راستہ: ایک ہی منظر کئی صفحات پر کام کر سکتا ہے |
| **اجزاء** | ایک دوبارہ قابل استعمال ٹکڑا ایک صفحہ درآمد کرتا ہے | ایک راستہ: سرور موڈ میں ایک جزو کبھی بھی اپنے طور پر پیش نہیں کیا جاتا ہے |
| **روٹ ہینڈلر** | کا کام a `.py` روٹ فائل، جسے HTTP طریقہ (`GET`، `POST`، …) | ایک صفحہ کے نام سے منسوب کیا گیا ہے: یہ JSON، ایک فائل یا `Response` |
| **اختتامی نقطہ** | جوڑا (URL، طریقہ) جس کا ایک ہینڈلر جواب دیتا ہے | ایک ہینڈلر: ایک فائل کئی اختتامی نکات کا جواب دے سکتی ہے |

ایک جملے میں: **ایک صفحہ ایک روٹ فائل ہے، ایک منظر وہ ہے جو اسے پیش کرتا ہے، ایک جزو وہ ہے جسے صفحہ دوبارہ استعمال کرتا ہے، ایک ہینڈلر جواب دیتا ہے اختتامی نقطہ**

دو مزید الفاظ جو ہر جگہ واپس آتے ہیں:

- **لے آؤٹ**: ایک `layout.*` فائل جو اپنے فولڈر کے نیچے صفحات کو سمیٹتی ہے۔ جڑ HTML دستاویز کا مالک ہے۔ دیکھیں [لے آؤٹ](../routing/fbr/layouts/README.md)۔
- **انحصار**: ایک فنکشن جو ہینڈلر سے پہلے چلتا ہے، فی روٹ یا فی فولڈر لاگو ہوتا ہے۔ دیکھیں [انحصار](../routing/fbr/dependencies/README.md)۔

## پیش کش اور پیش کش

دو آزاد فیصلے، اکثر الجھ جاتے ہیں:

- **فارمیٹ** فیصلہ کرتا ہے کہ کون سی فائل صفحہ کو رینڈر کرتی ہے: [ملاحظات](../views/README.md)۔
- **موڈ** فیصلہ کرتا ہے کہ HTML کون تیار کرتا ہے اور کب: [رینڈرنگ](../rendering/README.md)۔

| تصور | ایک سطر |
|---|---|
| سرور موڈ | سرور پیش کرتا ہے `.nexy` اور `.md` صفحات؛ اجزاء جزیرے ہیں ([موڈز](../routing/fbr/modes.md)] |
| کلائنٹ موڈ | `useCSR = True`: فریم ورک فائلیں راستے ہیں، اور نیویگیشن براؤزر میں ہوتی ہے |
| SSR، ISR، CSR، جزائر | چار رینڈرنگ موڈز، فی صفحہ طے کیا گیا سوائے CSR کے، جو فی پروجیکٹ ہے ([رینڈرنگ](../rendering/README.md)) |
| ہائیڈریشن | براؤزر جو HTML کے ساتھ فریم ورک کو منسلک کرتا ہے جو سرور نے پہلے سے بھیجا ہے ([جزیرے](../rendering/islands.md)) |
| پروپس | وہ اقدار جو والدین کسی جزو کو منتقل کرتے ہیں، `name: prop[type]` کا اعلان `.nexy` فائل ([.nexy فائلز](../views/nexy/README.md)) |

## درخواست کا تعامل

| تصور | ایک سطر |
|---|---|
| ایکشن | ایک Python فنکشن نشان زد `@Action`، ایک `POST` کے طور پر پیش کیا گیا، فارم سے کال کیا جا سکتا ہے یا ٹائپ شدہ فنکشن ([ایکشن](../guides/actions.md)]) |
| فارم | ایک ایچ ٹی ایم ایل فارم جو کسی ایکشن پر پوسٹ کرتا ہے، توثیق کی غلطیوں کے ساتھ صفحہ پر واپس آتا ہے ([ایکشن](../guides/actions.md)) |
| نیویگیشن | لنکس جو پیشگی حاصل کرتے ہیں، اور ہکس جو راستے، استفسار، کوکیز اور سیشن کو پڑھتے ہیں ([ہکس](../routing/fbr/navigation/hooks.md)) |
| ڈیٹا کی بازیافت | صفحہ یا ہینڈلر کے ذریعہ کی جاتی ہے جسے اس کی ضرورت ہوتی ہے۔ Nexy بغیر کلائنٹ ڈیٹا لیئر بھیجتا ہے ([ہینڈلر](../routing/fbr/handlers/README.md)]) |

## Nexy کیا نہیں کرتا

تصدیق، اجازت، ڈیٹا بیس، بین الاقوامی کاری، پس منظر کی ملازمتیں، ای میل، ادائیگیاں اور تلاش **آپ کی درخواست کی ذمہ داری** ہیں، نہ کہ فریم ورک کی۔ Nexy ایکسٹینشن پوائنٹ دیتا ہے اور کہتا ہے کہ ہر ایک کو کہاں سے لگانا ہے: دیکھیں [حدودیں](../architecture.md#boundaries)۔

وجہ اس کی اپنی خاطر minimalism نہیں ہے: ایک فریم ورک جو آپ کے ORM یا آپ کی auth لائبریری کو چنتا ہے اس نے کچھ فیصلہ کیا ہے جس کا فیصلہ صرف آپ کی درخواست ہی کر سکتی ہے۔
